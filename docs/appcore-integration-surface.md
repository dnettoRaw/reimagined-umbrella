# AppCore integration surface for PROEXEL - CONCLUÍDO 100%

Verified on 2026-08-15. AppCore remains a generic host; all entities and policies
listed here are owned by PROEXEL.

## Runtime contracts

The service is registered by `apps/service/application.toml` and runs through
the public AppCore application lifecycle. Scoped command/query tokens are
generated by `appcore-bin`; tokens stay server-side in `PROEXEL_SERVICE_TOKENS`.

Command envelope:

```json
{
  "command_name": "proexel.machines.create",
  "command_id": "unique-id",
  "idempotency_key": "unique-key",
  "issued_at_ms": 1786795200000,
  "payload": {
    "actor": { "id": "user-id", "name": "Name", "role": "admin" },
    "data": {}
  }
}
```

Queries use the corresponding query name, ID, actor and filter data. The web
adapter obtains identity from the signed session rather than accepting actor
fields from the browser.

## Ownership and persistence

AppCore provides capability validation and hosting. PROEXEL owns payload parsing,
domain policies, role checks, idempotency receipts, audit semantics and canonical
state. `JsonFileStore::transact` serializes writes and uses an atomic temporary
file replacement. No business entity was added to AppCore crates.

## Authentication

Password/PIN hashes are resolved only through the server-only identity query.
List and audit responses redact credential hashes. Session tokens include role,
user ID, auth version and maximum repair level; account updates invalidate old
sessions.

## Local launcher

`scripts/dev-stack.sh` rotates the three-hour runtime secret, emits one token for
every capability above, seeds a first-run administrator when needed, and starts
the Rust service and Next.js. The E2E launcher uses the same path with isolated
ports, state and attachments.
